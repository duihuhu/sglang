# DynamoLLM: Designing LLM Inference Clusters for Performance and Energy Efficiency

> **会议**: IEEE HPCA 2025  
> **作者**: Jovan Stojkovic, Chaojie Zhang, Íñigo Goiri, Josep Torrellas, Esha Choukse  
> **机构**: University of Illinois at Urbana-Champaign, Microsoft Azure Research

---

## 一、研究动机

LLM 推理集群消耗大量能源并产生大量碳排放，但现有能效管理方案主要针对传统数据中心 (CPU 频率调节等)，无法有效应对 LLM 推理工作负载的独特特性。LLM 推理环境存在以下挑战：

1. **请求异构性**: 不同输入/输出长度的请求具有截然不同的计算和能量特征
2. **负载动态变化**: 请求分布和负载强度随时间剧烈波动 (日夜/工作日-周末模式)
3. **多维配置空间**: GPU 频率、模型并行度、实例数量等配置旋钮形成巨大搜索空间

## 二、核心洞察

### Insight #1: 请求级能效异构性

| 维度 | 特征 |
|------|------|
| **请求长度** | 短请求 (SS) 可在 TP2 低频运行；长请求 (LL) 仅能在 TP8 运行 |
| **请求负载** | 低负载下 TP4@1.2GHz 最优；高负载需 TP4@2.0GHz |
| **模型类型** | 小模型 (13B) 可用任意 TP；大模型 (180B) 仅能 TP8 |
| **服务 SLO** | 宽松 SLO (10×) 可用更低频率配置，节省更多能耗 |

**关键发现**: 不同请求类型需要不同的最优能效配置，统一配置会导致严重的能量浪费。

### Insight #2: 工作负载的动态性

- **请求分布变化**: Coding 和 Conversation 两种服务的请求类型分布随时间显著变化
- **负载波动**: Coding 服务峰值是均值的 2.8×、谷值的 34.6×
- **SLO 多样性**: 不同服务可能共享同一 LLM 但有不同 SLO 要求

### Insight #3: 重配置开销不可忽视

| 操作 | 开销 |
|------|------|
| 新建 LLM 实例 | ~6-8 分钟 (VM 创建 + 环境初始化 + 权重下载) |
| 模型重分片 (re-shard) | 50ms - 数秒 (取决于并行度变化方向) |
| GPU 频率调整 | ~50-80ms (可能使推理延迟翻倍) |

## 三、系统设计: DynamoLLM

### 架构概览

DynamoLLM 采用**三层分层控制器架构**:

```
Cluster Manager (集群管理器)
├── 接收请求，预测类型，分发到对应池
├── 控制旋钮: 实例数量 (Scale in/out)
├── 调整周期: ~30 分钟
│
├── Pool Manager (池管理器) × N
│   ├── 管理池内实例的模型并行度
│   ├── 控制旋钮: 模型并行度 (Shard up/down)
│   ├── 调整周期: ~5 分钟
│   │
│   └── Instance Manager (实例管理器) × M
│       ├── 微调 GPU 频率
│       ├── 控制旋钮: GPU 频率 (Scale up/down)
│       └── 调整周期: ~5 秒
```

### 核心机制

#### 1. 基于 Profile 的能效优化

- **离线阶段**: 对模型在不同请求长度、负载、并行度、频率下进行 profiling
- **优化目标**: 最小化总能耗，约束为 GPU 数量、负载需求、SLO 性能
- **求解方式**: MILP (混合整数线性规划)

#### 2. 分层动态控制

- **Scale-out/in (30min)**: 根据负载预测，计算每个请求类型池的最小节点数
- **Shard-up/down (5min)**: 在给定 GPU 数量下选择最优模型并行度
- **Scale-up/down (5s)**: 在给定并行度下微调 GPU 频率

#### 3. 低开销重配置

- **实例扩缩**: 本地缓存模型权重 + VM 快照 + 后台预创建
- **模型重分片**: 图匹配算法最小化权重传输 + NVLink 直连 GPU 间并行传输
- **频率调整**: 预加载 nvidia-smi + 特权模式运行避免 OS 切换开销

#### 4. 请求异构处理

- 将请求按输入/输出长度分为 9 类 (SS, SM, SL, ..., LL)
- 使用 BERT 预测器分类输出长度 (准确率 81%)
- 误分类请求通过紧急机制处理 (重排序→频率提升→请求迁移→请求丢弃)

## 四、实验评估

### 实验环境
- **硬件**: NVIDIA DGX H100 服务器集群
- **模型**: Llama2-70B (主要)
- **Trace**: Microsoft Azure 生产级 Coding/Conversation 服务 trace

### 主要结果

| 指标 | DynamoLLM vs SinglePool |
|------|------------------------|
| **能耗节省** | 平均 52% |
| **碳排放减少** | 平均 38% |
| **用户成本降低** | 平均 61% |
| **P99 TTFT** | 降低 5.3% |
| **P99 TBT** | 降低 11.0% |

### 能耗拆解 (1h Conversation trace)

| 系统 | 能耗变化 (vs SinglePool) |
|------|------------------------|
| MultiPool | +20% (分配更多资源但全高频) |
| ScaleInst | -2% (仅缩放实例) |
| ScaleShard | -6% (仅调整并行度) |
| ScaleFreq | -19% (仅调频) |
| **DynamoLLM** | **-35% (联合优化)** |

### 敏感性分析

- **分类准确率**: 40% 误分类仅增加 25% 能耗，系统具有较强鲁棒性
- **负载级别**: 低/中/高负载分别节省 57%/42%/15%
- **池数量**: 9 个池为最优平衡点 (太少无法精细调优，太多导致碎片化)

## 五、关键贡献

1. 首次系统分析了 LLM 推理环境的能效优化机会
2. 提出 DynamoLLM——第一个针对 LLM 推理的能效管理框架
3. 分层控制架构同时优化实例数量、模型并行度和 GPU 频率
4. 低开销重配置技术支持频繁的动态调整
5. 在大规模生产环境下验证了显著的能效提升

## 六、局限性

- 需要离线 profiling，模型更新时需重新 profiling
- 输出长度预测准确率 (81%) 仍有提升空间
- 未考虑 prefill/decode 分离 (disaggregation) 架构
- 重配置开销虽然优化但仍需数十秒到分钟级别
- 未考虑 embodied carbon (硬件制造碳排放)
