## 1. 从M1递进的问题

M1已经观察到：相同token计量的请求集合具有不同的hybrid state/KV需求，且当前token-VTC下不同请求形态的租户承受不对称的混跑slowdown。它尚未证明固定state单独导致这些服务差异。

这里的“token成本不同”指单位token的资源成本不同，不是业务价值不同，也不是已经得到新的公平收费公式。短请求的固定state摊销高，不直接推出应少服务短请求租户；state-time还受到调度本身影响，不能把系统导致的等待未经分析就转成租户应承担的费用。

**M2现在的核心问题：当不同租户的单位token资源成本不同，现有基于token的公平计量如何经过排序、准入和组批转换成实际资源占用与服务分配？这种转换何时影响其他租户的服务机会与隔离，是否存在同一公平约束下可避免的损失？**

M1的成本差异作为已知前提，不在M2中从零重新证明。“固定我、改变邻居形态”是识别这条转换链的控制实验，不是用普通邻居干扰问题替代研究核心。这里只使用已有缓存资源成本结论，不预设完整计算价格或公平收费公式。

研究对象是公平排序与执行机制的组合，不是单独寻找最低平均JCT的batch配置。也不预设不同租户使用不同算法；同一个调度器根据请求形态和运行状态选择如何分配机会即可作为研究对象。

整体顺序明确为：

1. M1：相同token计量为什么不能充分表征不同租户的hybrid资源负担？
2. M2：这些差异如何经调度转换成跨租户服务机会与隔离差异？
3. M3：观察到的差异是否能由现有成本校准、记账时机或简单控制解释并修复？
4. 后续设计与效率评估：在公平目标明确且满足约束后，再探索如何更快完成请求、提高吞吐或SLO goodput。

效率始终要记录，用于防止以大量浪费换取表面公平；但单租户mean JCT下降不再是M2的主验收条件。

## 2. Hybrid进入公平调度的具体位置

在当前无prefix复用、无retraction的模型路径中，租户u的活跃缓存主体近似为：

\[
M_u(t) = S N_u(t) + K T_u(t).
\]

本机TP2每rank的state主体S为21,708,800 bytes/request，KV主体K为8,064 bytes/token。这是当前配置的测量口径，不作为所有hybrid模型的常数。

一个租户获得一次新请求激活，不只是得到本轮计算：它还建立持久state，可能改变其他租户后续能否激活。继续已有请求通常不重复支付该state；请求完成则释放自己的state和KV。组批又影响这些请求的推进、完成及释放时刻。

因此待验证的链路是：

> 邻居请求形态变化 -> 邻居的state/KV占用与执行组合变化 -> 目标租户的准入或推进机会变化 -> 目标租户的实际服务与混跑延迟变化。

固定state是否造成额外影响必须在链路中定位，不能只把资源图和延迟图并列。拆分请求也改变prefill计算形态、调度粒度和收费时刻，等token不等于等计算。

统一池可减少分区浪费，但不会使S消失；反过来，固定state有物理来源，也不代表必须有新算法。固定大小state的独立池可以表现为普通请求上限，cap对照复现阻塞不否定其内存来源，只限定现有控制是否足够。

## 3. 服务机会、服务公平与隔离分别是什么

不能用一个“fairness gap”代替全部判断。先分开记录，正式阈值在新实验协议中冻结。

| 观察层 | 每租户需要记录什么 | 能回答什么 |
|---|---|---|
| 公平计量 | 权重、实际scheduler counter、预记与校正、排序位置 | 调度器认为谁已获得多少服务、谁应被优先考虑 |
| 准入机会 | waiting队列、候选被考察/获准/拒绝时刻、实际拒绝分支及请求需求 | 排序靠前是否转换成实际激活；没有获准是资源不可行还是策略选择 |
| 执行进度 | 每批实际处理的prefill/decode token、已运行请求及进度间隔 | 获准后是否实际获得推进；batch参与次数不能替代工作量或GPU执行时间 |
| 持久资源 | 同时刻state/KV归属、增量需求、释放及后继请求激活 | 一方的资源持有是否限制另一方；state-time下降本身不等于公平改善 |
| 对外服务与隔离 | delivered输出、TTFT、TPOT/JCT、匹配独跑slowdown及绝对延迟 | 用户实际得到什么服务，邻居带来多少额外损失 |

本地token-VTC的权重口径仍可作为第一轮诊断参考。需要分别记录内部counter和实际处理/交付服务，不能把shadow input charge当作已执行工作，也不能把输入处理量当成客户端已收到的输出。按预先声明的权重归一化服务增量；若改变公平定义，必须另行标注，不能称为相同保证下的改善。

公平窗口至少须验证双方同时持续有待服务需求，并另外报告waiting-backlogged与仅有running请求的区别；扣除窗口开始时的累计值，说明窗口是否随策略改变。固定结束总token相同并不证明过程公平。短窗口中的请求粒度误差、不可抢占区间也应单独披露，不能把任意瞬时差距认定为保证被违反。

服务隔离不预设两租户绝对JCT相等，也不把等slowdown当作现有方法的承诺。用固定目标租户的邻居敏感性、各自匹配独跑结果、worst-tenant slowdown和全部租户绝对延迟共同评价。不通过拖慢较快租户来宣称公平提升。

## 4. 当前需要验证的三个问题

### F1：邻居的请求形态是否改变我的服务机会

本项检验“相同token计量、不同资源成本”如何转换成实际服务；邻居partition是控制手段，最终要解释计量、占用与服务进度的关系，而不只报告延迟变化。

固定目标租户A的请求、到达、输出长度和权重；比较A独跑、A与B-packed混跑、A与B-split混跑。B两种形态保持相同总输入/输出token及wave级到达计划，记录实际接收顺序；B自身形态的独跑结果也分别采集。再交换租户标签、先到顺序，并用短/长两种目标A做对称检查，避免将标签或固定到达优势写成形态效应。

先使用正确配置的池、请求表、slot门限和固定本地token-VTC，不因结果更换公平成本。保证存在可核对的共同积压窗口；有限burst没有该窗口时，只报告隔离/延迟观察，不给过程公平结论。

**应得到的问题或负结果：** 在目标自身不变、邻居总token与权重相同的条件下，目标的准入、执行服务和延迟是否仍显著依赖邻居partition？若只有总mean变化而无跨租户过程证据，本项没有完成。

本实验先识别跨租户形态效应，不声称其唯一原因是state，也不再次用同时改变两方shape的结果代替固定目标对照。

### F2：差异发生在公平计量到实际执行的哪一步

对F1的同一请求轨迹按租户对齐counter、队列、可行性检查、batch进度、state/KV持有和输出服务。区分三类路径：

- 计量/排序差异：请求粒度、input预记或output记账时刻已经改变了优先级。
- 准入限制：优先考虑的候选确实受state、KV、普通cap或其他budget限制；必须有实际需求和拒绝事件，而不是从占用峰值推测。
- 激活后的执行干扰：已获准但推进速度受邻居batch影响；这可能是通用计算/后端/workspace问题，不先归因KDA。

若观察到空间阻塞，再在同工作集、同普通cap、经完整内存预算核对的资源条件下检查阻塞的产生/消失，连接“邻居持有 -> 目标等待 -> 邻居释放 -> 目标获准”。池变更引入的workspace等差别必须披露；不将缩小cap直接称为固定state的独立消融。

**应得到的问题或负结果：** 哪个现有机制把邻居资源构成变化传递成了目标租户的服务损失？若宽容量下差异不变、也没有cache拒绝，就将该解释归入计量或执行干扰，不强行称为state容量介导。

### F3：是否存在同一公平约束下可避免的隔离损失

固定公平计量和权重，只对已定位的准入/组批动作做少量、预先规定的诊断干预；先给原生cap/chunk/延迟控制训练调参机会，再冻结到另一种请求形态或到达轨迹。确认干预实际触发，不把关闭或未触发的控制当成先进方法失败。

同时检查：目标租户绝对延迟与worst-tenant slowdown是否改善，另一租户是否承担不可接受的损失，共同积压窗口的服务分配是否满足相同口径的公平约束，整体效率代价是否在预先冻结的范围内。所有数值阈值必须在正式结果之前写入协议，不能直接搬用旧单租户5%门槛冒充新的公平约束。

**应得到的问题或负结果：** 若有满足共同约束的局部替代动作，可支持“当前组合存在可避免的隔离损失”；若只靠牺牲另一租户、改变公平定义或仅降低整体mean，则不能支持该命题。发现问题不要求先超过所有SOTA，但声称新机制必要或论文设计贡献时仍需更强对照。

F1--F3是新的研究问题编号，不替代历史E1--E3；F1观测功能预检已完成，正式确认和F2/F3尚未PASS。顺序为先F1、再据轨迹选择F2干预，最后F3；暂不继续以单租户Decode32收益为目标扩大矩阵。

## 6. 当前结论和下一步

**已经知道：** 请求形态影响hybrid资源需求；在现有本地公平策略下观察到服务隔离差异；准入/组批能改变两个租户的服务结果；原容量与实现问题中的一部分已有修复方式。

**还不知道：** 在正确配置和明确公平口径下，邻居的固定state/KV占用通过哪条实际调度路径影响目标租户；现有组合是否因此留下同一公平约束下可避免的隔离损失。

旧双租户轨迹审计和[新只读观测功能预检](m2_service_preflight_results_20260918.md)均已完成。新数据可区分收费/lift、候选是否selected、已完成计算与资源生命周期；尚不能精确标注每个`OTHER`内部分支或allocator释放原因。固定目标下出现邻居形态敏感性，但更高state占用并不单调对应更大干扰；本轮无容量拒绝，不能将其写成state wall因果。

下一步先预检更长的共同积压窗口、独立量化观测开销并核对通信backend，然后冻结正式F1矩阵、重复/镜像与公平口径。不得把相同最终token、相同最大counter gap或单个p95改善当作完整公平结论。不预设lifetime predictor、资源向量计费或按租户分开执行。

新的主线是：**先解释hybrid如何改变租户之间的服务机会与隔离，再在公平要求明确的条件下探索效率优化。** “如何更快完成一批请求”属于后续问题，不再替代M2。
