# M2：从相同token计量到不同租户服务的历史轨迹审计

2026-09-17。沿新主线完成第一步：远端只读复核60组历史确认数据、8000请求，其中20组双租户混跑、40组匹配独跑；所有原始SHA256与原分析索引一致。**本轮新增GPU性能样本为0，未修改历史PASS/FAIL。**

## 1. 本轮回答什么

以M1“单位token资源成本随请求形态变化”为前提，检查已有双租户实验能否回答：**相同token计量经过公平排序、准入和组批，形成了怎样的租户资源占用与实际服务？**

本轮不是重新寻找最低mean JCT，也不再用单租户Decode32作为公平改善证据。审计得到三项可复核观察，并确认了补测不可缺少的事件。

数据来自9月9日至10日的f16/f32确认，每个形态、cap有5次配对运行。各租户均为131072 input + 4096 output，最终按`input + 2*output`计量均为139264。f16短租户128请求，f32短租户256请求；长租户始终8请求。两cap同形态、同rep的完整payload fingerprint一致。

## 2. 观察一：同样完成token，资源占用不同，且占用受执行控制影响

以下是短租户/长租户的完整运行资源积分比，先逐rep求比，再平均；两者最终token charge相同，因此也等于相应per-charge资源积分比。

| 形态 | 运行cap | State slot-time比 | KV token-time比 |
|---|---:|---:|---:|
| f16 | 96 | 4.819 | 0.307 |
| f16 | 48 | 2.791 | 0.178 |
| f32 | 96 | 5.634 | 0.179 |
| f32 | 48 | 3.069 | 0.098 |

**Observation：同样的token计量对应不同资源构成；相同请求和计量下，改变准入也会改变这种实际占用差异。** 短租户的state积分更大，但KV积分更小，不能说它在所有资源上都更贵。

**Insight：M1中的固定state摊销是请求形态的结构性成本；运行中的resource-time还受到准入、执行与等待影响。后者不能未经分析就变成租户应支付的公平费用。** 这将M1的成本差异接到M2的执行后果，而不是直接推导“对短请求加税”。

口径限制：旧数据的state-slot-seconds / active-request-seconds对两个租户、全部20组均为3.0；配置readback为radix未关闭、CUDA graph未全关闭。state指标包含当时实际分配的额外缓冲，不能套用最新radix-off、一请求一份state的数值，也不能把state和KV的独立积分相加成同一时刻物理显存。resource-time不是独立GPU计算时间，更不是固定state对延迟的单因素效应。

## 3. 观察二：尾延迟改善和获得服务的时序不是同一件事

从客户端完整累积输出流重建每租户获得其总输出50%的时刻。时间从各run共同的计划起点计，不是单请求提交后的JCT，也不包括输入处理量。

| 形态 / 租户 | Cap96 p95 JCT，s | Cap48 p95 JCT，s | Cap96 输出50%，s | Cap48 输出50%，s |
|---|---:|---:|---:|---:|
| f16 / 短 | 10.635 | 7.825 | 10.390 | 10.729 |
| f16 / 长 | 19.994 | 20.116 | 17.399 | 17.775 |
| f32 / 短 | 7.097 | 7.071 | 11.357 | 8.987 |
| f32 / 长 | 20.140 | 20.197 | 17.605 | 17.921 |

表中均为5次均值，新输出指标是事后描述性分析，没有新增确认性CI。原p95 gate保持不变：f16短p95配对改善26.42%，f32为-0.40%、CI跨0；不能用表中均值比替代原逐配对估计。

f16的5个配对中，短租户p95均改善，但输出50%时刻均更晚，长租户输出50%也均更晚。f32则在5个配对中都更早达到短租户输出50%，但原短p95确认没有稳定收益。它们不存在统计定义矛盾：请求尾延迟和跨请求的输出交付进度观察的是不同对象。

**Observation：保持token-VTC及最终token工作量不变，准入控制可以向不同方向改变租户尾延迟与服务交付时序。**

**Insight：不能把“短租户p95改善”直接翻译为“它更早获得服务”或“公平改善”；也不能把p95 gate未通过翻译为“服务分配完全没改变”。** 应同时观察计量、准入、执行和交付，明确究竟要保护哪个服务目标。

## 4. 观察三：旧公平计数汇总不能解释实际服务轨迹

f16的每个rep中，cap96和cap48的VTC最大counter gap、最终counter gap分别完全相同；但第3节的资源占用和交付时序不同。其计数器记录只有`observation_count`、`max_counter_gap`、最终`counters`和queue wait汇总，没有中间事件。

**能说：相同的最大/最终计数差汇总不足以刻画实际服务轨迹。不能说：两次运行的完整计数轨迹相同，或VTC公平保证失效。** 未记录的counter lift、排序、积压条件和准入差异不能从最终值逆推。

作为额外描述，本次对每个cap配对使用同一个客户端时间窗：从两run最晚的实际提交开始，到两run中最早出现某租户全部完成为止；扣除窗口起点的输出量。这段区间两方仍有客户端未完成请求，但不保证服务端waiting-backlogged。

| 形态 | 共同窗口平均时长，s | Cap96最大输出增量比例差，均值 | Cap48对应值 |
|---|---:|---:|---:|
| f16 | 4.365 | 33.54% | 32.78% |
| f32 | 4.341 | 55.59% | 26.13% |

分母是每租户全run的4096输出token，按同一时间窗计算增量，排除输入；窗口终点由完成结果决定。这些数字**不是token-service fairness、不是VTC bound测试，也不是同公平约束下的收益**，只展示交付过程可以进一步测量。后续正式公平判断不能沿用这个事后drain window冒充合法积压窗口。

## 5. 哪些证据确实缺失

| 字段 / 能力 | 20组双租户混跑中的覆盖 | 影响 |
|---|---:|---|
| 完整客户端输出流 | 20/20 | 可复核交付时序 |
| VTC计数汇总 | 20/20 | 只知最终和最大差距 |
| VTC逐事件counter、lift和排序 | 0/20 | 不知某决策时刻谁应被优先考虑 |
| 每租户resource-time汇总 | 20/20 | 可比较整段资源占用 |
| 资源激活/释放事件 | 0/20 | 无法连接某方持有到另一方获准 |
| Batch形态、tenant_counts | 20/20 | 可见参与构成，不是逐租户实际工作量 |
| 每请求batch工作量、按租户waiting快照 | 0/20 | 无法核验处理服务或双方持续等待 |
| 候选检查/拒绝记录 | 0/20 | 没有拒绝记录不等于没有拒绝 |
| 服务端绝对事件原点及客户端绝对起点 | 0/20 | 无法精确拼接两侧时钟，不能靠拟合偏移补成事实 |

此外，旧f16/f32对照只验证了各自cap配对的完整payload一致性，没有固定目标租户的跨形态独立fingerprint。两者分会话运行，原runner的canonical run ID包含factor，输入生成也使用run ID作为种子材料。因此不把f16/f32间差异当作“同一目标A，只改变邻居B”的严格F1对照。

## 6. 对新M2的推进与最小补测

本轮把已有证据整理为：

> 同样最终token计量，资源占用构成不同；同样的公平排序和工作量，执行控制改变实际资源占用与租户服务时序；仅看counter汇总或单个延迟指标不能解释这种转换。

这是新的问题组织和旧轨迹的新分析，不是已经证明“hybrid独有的公平缺陷”。特别是旧cap96/48和带额外缓冲的cache配置不能代表正确统一池下的全部能力。

下一步不是继续扫单租户cap，而是先补齐事件可观测性，再进行[固定目标/改变邻居的补测规格](m2_tenant_service_f1_measurement_spec_20260917.md)：

1. 固定A的payload、到达和权重，仅改变B在相同token需求下的partition，先检查跨租户服务分配变化。
2. 用共同事件序列连接counter与排序、候选检查、实际激活、工作推进和释放；分开计量差异、容量阻塞、计算干扰。
3. 先确认问题与机制，再以同一公平口径评价简单干预，最后才进入“更快完成一批请求”的效率优化。
