
High Scalable Hierarchical Namespace Management for Trillion Objects and Data-Intensive Applications

1. Introduction
[规模非常大]
大型互联网公司往往需要管理大量的数据。百度在内部的文件系统上管理了上千亿的文件，并且近年来规模还在持续增长，对层级namespace的高效管理提出了挑战。

[性能要求高]
百度基于这些文件系统上构建了数据密集型应用，包括对象存储上的 Hive、Spark 作业 和基于文件系统的大模型训练、语音识别等应用。 而数据密集型应用在执行的过程中会大量访问元数据。

[亟需大规模、高性能的层级 namespace 管理]
以大数据常见的 ETL （提取-转换-加载）任务为例，即使文件平均大小已经达到110MB，在分布式文件系统上运行时元数据耗时依然达到了总体时间的60.8%；同时，用户大量的在线计算需求也对元数据操作的低尾延迟提出了要求。

除文件系统外，百度在云上提供了对象存储来服务大量的外部大数据客户，目前单个大数据用户的存储需求已达数十亿。然而，由于对象存储扁平的结构管理，目前大数据应用的性能受限于缓慢的目录操作，也亟需大规模的层级namespace 管理。

[层次化元数据管理系统的要求]-单独章节总结分析百度内部的workloads
结合以上需求，百度想要做一个大规模、高性能、层次化的元数据服务系统。具体要求：

--Scale的要求
要求支持百亿对象的层级namespace（业界报告表明，一个数据中心内会存在大量的十亿级别的 namespace，总量在万亿级别）；而我们分析百度云内部的信息，最大的用户已经超过了20/30亿；
允许一个目录下面的对象数目超过1000万（大模型训练、语音识别等工作负载下发现有数十万大小的目录、P2P 下载场景一个目录下有600万子目录）；

-- 满足极端的的workload 
生产系统的workload分析：
1.lookup 占比最高(所有文件操作都依赖 lookup 获取 inode)
2.访问深度集中在十层以上（lookup 开销在 ms 级别）
3.目录 rename 操作罕见，但峰值高（实时大数据任务产生大量并发目录rename)
4.超大目录下存在 bulk deletion（数据生命周期导致同时同目录下文件被同时删除）

-- 高性能且稳定
需要1M QPS的 lookup 查询性能；
需要在生产系统中的极端场景下稳定工作，且要满足在线大数据业务，需要保证低的尾延迟；


现有系统通过采用解耦元数据存储层，并划分到分布式数据库的方法，能够实现高可扩展的元数据管理，但是无法满足百亿级别可扩展下高性能和低延迟的要求。

[现有的research和开源系统满足不了上面的要求]
现有的对象、文件存储均无法满足应用对元数据性能的需求：
1. 对象存储的扁平结构为目录操作引入额外开销：如目录 rename 需要 copy+delete 所有子文件，而readdir 则要前缀扫描整棵子树。以大数据常见的 ETL （提取-转换-加载）任务为例，在以对象存储作为存储后端的情况下，对6.6T 数据数据集（共6W个文件，平均1.1G）执行 ETL 作业，仅 rename 操作的开销就占比69.4%。

2. 文件系统在大数据场景下性能极差：目录树深度高，文件系统元数据操作性能低下。如 lookup、rename 等目录相关的元数据操作的延迟随子树大小上升而上升（引用 InfiniFS、HopsFS、Tectonic、CFS等文章），性能无法满足大数据场景的需求；

[设计概述]
我们设计并实现了\sysname来满足下一代元数据的管理，follow CFS的方案，使用一个大规模的分布式数据库解决存储百亿层级 namespace 的问题。这样做可以解决存储问题，但需要解决元数据的性能挑战：

[Challenges]
(1) lookup占比很高，性能至关重要，但是lookup 是个递归查询（如查/a/b/c/d 要依次查a, b, c, d），现有方法均无法满足万亿场景下的高性能lookup;
(2) 目录 rename 是文件系统中最复杂的操作，现有的论文中往往认为目录 rename 占比较低，所以为了正确性而牺牲了目录 rename 的性能。但我们发现生产系统中存在 rename burst 问题，导致系统明显卡顿；
(3) readdir操作是层级 namespace 中最常见的目录读取操作，但存储系统中常见的异地更新操作导致生产系统中的大目录下 readdir 尾延迟很高；

[实现的概述]
针对 (1)结合了dtree分片存namespace sketch，并进一步使用混合索引的方法来满足lookup的高性能。满足了高可扩展性的要求，并且lookup的性能也很高；
针对（2）轻量级的环检测与异步的 cache invalid 策略，在保证 namespace 语义正确性的同时提供高性能；
针对（3）墓碑感知的 GC 策略 + 内存MVCC机制，保证千万级别的目录下 readdir 仍然低延迟；

综上：我们实现了\sysname系统，同时为文件、对象场景下的大数据应用提供百亿级别的高性能层级 namespace；

[本文的贡献]
贡献1：解决了一系列的技术挑战，提高了lookup、rename的性能。
贡献2：构造了系统，能够替换原来的元数据服务。管理的规模提高2~3个数量级。
贡献3：实验表明，实验效果如何。

2. Background and Motivation
2.1 Need for Large-Scale Namespace
百度的生产数据显示需要更大规模的namespace：
1.用户的namespace规模在不断增长，而最大的五个namespace规模都超过了20亿，大于先前相关工作中支持的10亿级namespace
2.数据密集型应用给namespace中的目录管理的容量和性能带来了更大的挑战
a.大模型训练和语音识别任务中存在大量的对百万级目录进行list的操作
b.p2p下载任务中，一个目录可能存在大于六百万个子目录
3.小规模的namespace导致 需要维护大量的集群，成本高昂且资源利用率低
我们的目标：构建百亿规模的namespace
2.2 Metadata Performance is Critical
元数据性能对数据密集型应用很重要
1.lookup：所有元数据操作都需要先执行lookup以得到inode，这意味着lookup操作性能决定了namespace的总体性能。根据生产环境中的统计，一个小时级别的大数据作业中50%的元数据操作都是 lookup，时间开销达到 XX%；
2.目录rename：在实时大数据分析场景下，一个6TB的数据集通过分区并发执行的方法，仅需要10s 钟即可完成数据读取与分析，但结束时产生的上千个并发目录 renmae 需要10分钟来完成。
（细节数据待本周在生产系统上测试）
2.3  Limitations of Existing Solutions
① 现有做法均无法做到百亿级别下高可扩展与lookup高性能
    1. 子树分区：扩展性受限于负载均衡，且 lookup 开销随子树分裂次数上升而上升； 
        例子：CephFS、CubeFS 
    2. 哈希分区：lookup 需要逐层递归查询，元数据操作延迟高昂； 
        例子：InfiniFS、JuiceFS、CFS、HopsFS、DAOS 
    3. 并行路径解析：通过预测元数据的物理位置的方法，可以将 lookup 的递归查询并行化来减少latency，但：①在 rename 较多的情况下lookup 性能会退化； ② 为 lookup 引入了检查 rename list 的额外开销；③ rename 操作需要广播所有 mds，开销高昂。
        例子：InfiniFS
    4. 中心化目录节点：将目录元数据与文件元数据分离，目录元数据存储在一个中心节点上，减少 lookup 的 RPC 次数，但：1. 文件系统语义规定了除文件属性读写外的所有元数据操作都需要读或写目录的元数据，导致中心节点请求压力巨大；2. 内存容量难以满足百亿级别文件系统需求)；可扩展性不足
        例子：LocoFS 

② 难以同时满足 rename 操作的高性能与正确性
目录 rename 是文件系统中最复杂的操作，现有的论文中往往认为目录 rename 占比较低(小于万分之一)，性能不重要，但我们发现生产系统中存在 rename burst 问题：
    ①峰值高：单用户每秒2k 目录 rename，持续10s 以上；
    ②持续时间长：rename > 1k/s，持续3小时以上；

性能难题：由于并发的目录 rename 有可能产生孤儿环，若不对并发 rename 进行冲突检测，则有可能丢失数据（JuiceFS）；而正确实现目录 rename 则开销高昂。
    1. 传统做法：全局 rename lock ，完全无法并发 （HDFS、Linux 内核）
    2. 子树粒度锁: 开销随子树大小而上升，以hopsFS 数据为例，rename 需要亚秒级别的开销。（LocoFS，HopsFS）
    3. 中心节点环检测: 锁住公共父节点导致rename 的并发度低（CFS），且可能引入广播（infinifs）
导致问题：文件系统出现明显的卡顿；

③ readdir 操作的尾延迟在大规模下很高
readdir操作是层级 namespace 中最常见的目录读取操作，通过游标依次读取目录下的一定数量的子文件列表。然而由于广泛使用的生命周期机制，千万级别的大目录下存在大量的删除，保证 readdir 操作的低尾延时十分困难。
    挑战：为了减小写放大，out-of-place update 的策略在数据库中被广泛使用，比如事务层面 MVCC 机制和存储层面 LSM-Tree 的墓碑删除机制。这导致了大目录在存储时着海量的墓碑，从而在进行范围读取时会产生海量的无效扫描，极大地增加了尾延迟

3. \sysname Design
3.1 \sysname Architecture
主要讲体系结构方面的内容。解释一下各个模块。

3.2 Lookup Performance 
1. 解决单点支持存储百亿 namespace 目录树的容量挑战： 
    每个 namespace 构建一个中心化的 dtree 节点，存储 namespace 的 sketch(只存储目录inode和ACL，不存储属性)，保证在百亿级别下，lookup能使用一次 rpc 完成；   
2. 解决单点处理百万 lookup 的性能挑战：
    ①将开销较大但与目录结构无关的元数据操作（文件读写、readdir）从 dtree 节点分流，减少 dtree 节点的计算压力；
    ②根据文件分布集中在叶子节点的特性，设计低内存占用、聚合 acl 的 lookup cache，将 lookup 的内存查找次数减小到常数量级；

3.3 Tail Latency Reduction in rename
轻量级 rename 锁机制、rename 异步更新缓存机制
在 dtree 聚合了目录 id 的基础上：
    1. 设计了一套轻量级的环检测机制，在保证目录 rename 的正确性的基础上提升并发度；
    2. rename 时需要invalid lookup cache 中的条目，我们设计一种异步的cache invalid策略，来保证 rename 在常数时间完成。

3.4 Conflict between Scan and GC
内存 MVCC + 精确感知删除Range进行compact的机制
我们的做法：
    ① 墓碑感知的 GC 策略，加速大目录下的连续墓碑回收；
    ② 根据事务不超过5s的特性，设计内存 MVCC 机制，消除分布式数据库产生的额外墓碑。
