# 分析笔记：异构 PDAF 能耗交叉点 vs 真实 Azure 负载分布

## 1. 背景

为定位「异构 prefill-heavy PDAF（2PA4PF, P6+D2）何时能耗低于同构 Sym（P4+D4）」，
做了受控合成实验（图 `8gpu_energy_crossover_il_sweep.png`）。本笔记记录该实验与真实
Azure trace 分布对照后发现的现象与局限。

## 2. 合成实验设置（交叉点实验）

- 数据集：`workload_xover_il{2048,4096,6144,8192}_ol8_q2.jsonl`（合成，非真实 trace）
- 控制变量：**固定 OL=8、QPS=2**，只扫输入长度 IL
- 目的：隔离单一变量，回答「输入多长时异构开始反超」
- 对比方案：`pdaf_8g_2pa4pf_tier`（异构）vs `pdaf_8g_dyn_tier`（同构），均开 Tier DVFS

### 结果

| IL (OL=8) | 异构 2PA4PF | 同构 Sym | 异构省能 |
|---|---|---|---|
| 2048 | 156.1 kJ | 156.1 kJ | 0%（持平） |
| 4096 | 156.2 kJ | 156.7 kJ | -0.3%（持平） |
| 6144 | 182.8 kJ | 195.5 kJ | **-6.5%** |
| 8192 | 245.2 kJ | 257.7 kJ | **-4.9%** |

**交叉点落在 IL≈4096~6144**：低于此异构无优势，高于此异构省能 5~6.5%。

## 3. 与真实 Azure trace 的分布对照

真实 trace 的输入/输出长度统计：

| 数据集 | IL 中位 | IL p90 | OL 中位 | OL p90 | IL/OL 中位 |
|---|---|---|---|---|---|
| code_light | 1795 | 7212 | 9 | 37 | ~199 |
| code_medium | 2026 | 4605 | 9 | 37 | ~205 |
| code_heavy | 2341 | 6002 | 10 | 50 | ~208 |
| conv_light | 933 | 3887 | 41 | 418 | ~28 |
| conv_medium | 911 | 3583 | 42 | 360 | ~26 |
| conv_heavy | 833 | 3236 | 42 | 336 | ~26 |

## 4. 核心现象

### 现象 1：OL 极端（=8）在真实 code 负载里是常态，不是人为编造
code 类（代码补全）输出中位数仅 **9~10 token**，与合成实验的 OL=8 几乎一致。
所以「输出极短」这一维度，真实 Azure code trace 完全吻合。

### 现象 2：IL 维度真实数据偏短，大多落在交叉点左侧
真实 code 负载 IL 中位 ~2000，正好在交叉点（4096~6144）**左侧**，即异构尚无优势区。
只有少数长输入请求才进入异构占优区。

### 现象 3：落在「异构占优区」(IL≥6144) 的请求占比很低

| 数据集 | IL≥4096 占比 | IL≥6144 占比 |
|---|---|---|
| code_light | 15.9% | 14.2% |
| code_medium | 18.7% | 7.9% |
| code_heavy | 17.1% | 9.4% |
| conv_light | 8.3% | 1.5% |
| conv_medium | 7.6% | 1.5% |
| conv_heavy | 6.2% | 1.4% |

即使最有利的 code 类，也只有 **~8~14%** 的请求落在异构明显占优区（IL≥6144）；
conv 类几乎可忽略（~1.5%）。

### 现象 4：真实负载不会出现「持续」的 prefill 主导时间段
合成实验是整段 IL=8192/OL=8 **恒定**；真实 trace 是混合分布——
短输入请求占多数（中位 2000），长输入仅尾部（p90 才 4600~7200）。
不存在「一整个时间窗全是 IL≥6144 请求」的理想 prefill 主导段。

## 5. 结论与含义

1. **合成实验证明了机制存在**（异构在 prefill 主导时确实省能 5~6.5%），
   但**高估了真实可达收益**——真实负载中触发该优势的请求仅占少数尾部。

2. 这解释了为何**真实 Azure trace** 测 code_medium 时，
   异构 2PA4PF（11605 mJ/tok）仅**略优于** Sym（12808），
   而非合成实验中清晰的 5~6.5%：真实 IL 分布跨在交叉点两侧，被中位短请求稀释。

3. **机制存在 ≠ 真实能省多少**：要量化真实收益上限，需按真实 IL 分布加权，
   而非看单点合成结果。

## 6. 待办（量化真实收益）

- 按真实 Azure code trace 的 IL 分布加权，估计异构方案的**实际可达节能上限**
  （区分「机制收益」与「分布加权后的真实收益」）。
- 考察是否存在**局部时间窗**（burst）内长请求富集，可由 Tier1 动态切换到异构布局获益；
  若长请求在时间上均匀分散，则动态切换收益有限。
