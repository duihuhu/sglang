# 无 CUDA Graph 并发容量对照测试报告

## 1. 测试目的

在相同模型、硬件、内存配置和 workload 下，对比以下三种部署在**关闭 CUDA Graph** 时的：

1. 输出吞吐与延迟表现；
2. 最大完整成功并发；
3. 关闭 CUDA Graph 后，纯 TP4 在并发 1024 附近是否仍出现容量或性能断崖；
4. 标准 EP4 与 `ampere_ep` EP4 是否仍具有并发容量优势。

## 2. 环境与统一参数

| 项目 | 配置 |
|------|------|
| 容器 | `moe-energy` |
| GPU | 4× NVIDIA A800-SXM4-80GB（`CUDA_VISIBLE_DEVICES=0,1,2,3`） |
| 模型 | `/models/Qwen3-30B-A3B`（BF16，128 experts，top-k=8） |
| MoE runner | `triton` |
| 静态显存占比 | `--mem-fraction-static 0.85` |
| CUDA Graph | `--disable-cuda-graph`（日志确认 `cuda graph: False`） |
| 环境变量 | `FLASHINFER_DISABLE_VERSION_CHECK=1` |

统一 workload：

- dataset：`random-ids`
- 输入长度：32 tokens
- 输出长度：256 tokens
- `--random-range-ratio 1`
- `--tokenize-prompt`
- `--request-rate inf`
- `--seed 42`
- `--warmup-requests 0`
- 每个并发点 C：`--num-prompts C --max-concurrency C`

## 3. 三种服务配置

| 配置 | 启动参数 |
|------|----------|
| **纯 TP4** | `--tp-size 4 --dp-size 1 --ep-size 1 --moe-a2a-backend none` |
| **标准 EP4** | `--tp-size 4 --dp-size 4 --ep-size 4 --enable-dp-attention --moe-a2a-backend none` |
| **Ampere EP4** | `--tp-size 4 --dp-size 4 --ep-size 4 --enable-dp-attention --moe-a2a-backend ampere_ep` |

配置切换时通过 `docker stop` / `docker start` 重启容器，确保任一时刻只运行一个服务。

## 4. 成功判据与验证结果

每个并发点需同时满足：

1. `completed == C`（成功请求数等于目标并发）；
2. `total_output_tokens == C × 256`；
3. benchmark exit code = 0，JSON 可解析且字段完整；
4. 测试结束后服务 health check 通过；
5. server 日志中 `cuda graph: False`，无 CUDA OOM / Traceback。

**本次测试验证情况：**

- 三组配置在 C = 512、1024、2048、4096、6144、8192、**10240** 全部完整成功；
- 所有 JSON 的 `completed` 与 `total_output_tokens` 均精确匹配；
- 三个 server 日志均无 `CUDA out of memory` 或 `Traceback`；
- **未能获得首个明确失败点**，因此只能说「已验证下限 ≥ 10240」，不能给出容量上界或失败区间。

## 6. 横向分析

### 6.1 纯 TP4 在 1024 没有吞吐断崖

关闭 CUDA Graph 后，TP4 从 512 到 1024 输出吞吐 **+61.4%**（6,029 → 9,731 tok/s），1024 到 2048 **+19.3%**（9,731 → 11,613 tok/s）。峰值出现在 **C=2048（11,613 tok/s）**，4096 略回落至 10,624 tok/s。

**结论：关闭 CUDA Graph 后，TP4 在 1024 不存在性能断崖，反而随并发上升而提升，直至 2048 达到峰值。**

### 6.2 EP4 相对纯 TP4 的吞吐优势

同并发下，标准 EP4 / Ampere EP4 相对 TP4 的输出吞吐变化：

| C | 标准 EP4 vs TP4 | Ampere EP4 vs TP4 |
|---:|---:|---:|
| 512 | +1.1% | 0.0% |
| 1024 | **+12.3%** | **+14.8%** |
| 2048 | **+18.9%** | **+21.3%** |
| 4096 | +10.6% | +10.4% |
| 6144 | -1.2% | -0.9% |
| 8192 | +1.2% | +3.4% |
| 10240 | -0.1% | +3.0% |

EP 优势主要集中在 **C=1024–4096** 区间（约 +10% ~ +21%）。512 基本持平；6144 以上三组吞吐接近（~10.5k–10.9k tok/s），差异被调度排队掩盖。

### 6.3 Ampere EP4 相对标准 EP4

| C | 吞吐变化 | TPOT 变化 |
|---:|---:|---:|
| 512 | -1.1% | +2.7% |
| 1024 | **+2.2%** | -2.1% |
| 2048 | **+2.1%** | -2.0% |
| 4096 | -0.2% | -0.4% |
| 6144 | +0.3% | -0.6% |
| 8192 | +2.1% | -2.1% |
| 10240 | +3.1% | -3.8% |

`ampere_ep` 在中高并发（1024–8192）多数点略优于标准 EP4（约 +0.3% ~ +3.1%），但幅度较小，不构成决定性优势。高并发下 `ampere_ep` 的 TPOT  consistently 略低（约 2%–4%）。

### 6.4 延迟与排队行为

高并发（≥6144）时延迟急剧上升，但三组表现分化明显：

| C | TP4 TTFT | 标准 EP4 TTFT | Ampere EP4 TTFT |
|---:|---:|---:|---:|
| 1024 | 2,557 ms | 1,788 ms | 1,724 ms |
| 6144 | **40,132 ms** | 7,240 ms | 7,558 ms |
| 10240 | **92,897 ms** | 13,119 ms | 13,317 ms |

- **TP4 高并发 TTFT 远高于 EP4**：C=10240 时 TP4 mean TTFT 达 92.9s，而 EP4 约 13.1–13.3s。说明 DP attention 将请求分摊到 4 个 DP rank，显著缓解单 rank 排队导致的首 token 延迟。
- **EP4 高并发 TPOT 很差**（C=10240 时 ~850–883 ms），但 `ampere_ep` 略优于标准 EP4（849 vs 883 ms，约 -3.8%）。

## 7. 容量与 OOM 分析

### 7.1 为何关闭 CUDA Graph 后未复现 OOM？

在启用 CUDA Graph 的 `ep-test.md` 测试中，纯 TP4 在 C=4096、标准 EP4 在 C=6144、`ampere_ep` 在 C=10240 均因 logits TP AllGather 临时张量分配失败而 OOM。本次关闭 CUDA Graph 后，**三组均完整通过 C=10240**，未观察到任何 CUDA OOM。

server 日志观测到的调度行为：

| 配置 | 日志峰值 running-req | 日志峰值 queue-req | 日志峰值 token usage |
|------|---:|---:|---:|
| 纯 TP4 | 4,096 | 6,144 | 0.46 |
| 标准 EP4 | 2,560 | 1,470 | 1.0 |
| Ampere EP4 | 2,560 | 1,058 | 1.0 |

关键观察：

1. **Scheduler 分批运行**：TP4 在 C=8192/10240 时，实际同时 running 的请求被限制在约 4096，其余在 queue 中等待（例如 C=8192 时出现 `#running-req: 4096, #queue-req: 4096`）。这避免了同时构建过大的 logits / 临时张量。
2. **关闭 CUDA Graph 改变了调度路径**：eager 模式下不存在 CUDA Graph bucket 对 batch size 的约束，scheduler 可以更灵活地控制每步 batch 大小，从而绕开了启用 CUDA Graph 时的瞬时显存峰值。
3. **代价是极高的排队延迟**：高并发下 TTFT 和 TPOT 大幅上升（C=10240 时 TTFT 13–93s，TPOT 337–883 ms），服务虽能完成全部请求，但实际延迟不具备生产可用性。

**注意**：日志中 `token usage: 1.0` 出现在 EP4 高并发阶段，但服务健康且请求完整成功，**不应将其直接解释为 OOM 前兆**。这更可能是日志采样窗口内的瞬时峰值。

### 7.2 容量结论

| 配置 | 已验证最大完整成功并发 | 首个失败并发 |
|------|---:|---|
| 纯 TP4 | **≥ 10240** | 未观测到 |
| 标准 EP4 | **≥ 10240** | 未观测到 |
| Ampere EP4 | **≥ 10240** | 未观测到 |

关闭 CUDA Graph 后，原先在 CUDA Graph 模式下观测到的 OOM 容量边界（TP4@4096、EP4@6144、ampere_ep@10240）**均未复现**。但这并不意味着容量无限——只是 scheduler 通过排队避免了瞬时显存峰值，以延迟换取了更高的并发容忍度。

## 8. 总结

1. **关闭 CUDA Graph 后，TP4 在 1024 无吞吐断崖**，峰值在 C=2048（11,613 tok/s）。
2. **EP4 吞吐优势集中在 C=1024–4096**（相对 TP4 约 +10% ~ +21%），与 `ep-test.md` 中 CUDA Graph 开启时的结论一致。
3. **`ampere_ep` 相对标准 EP4 收益小但稳定**（中高并发约 +0.3% ~ +3.1% 吞吐，TPOT 略优 2%–4%），不构成决定性差异。
4. **三组在 C=10240 均完整成功**，关闭 CUDA Graph 消除了原先的 OOM 容量边界，但代价是极高的排队延迟。
5. **DP attention 显著改善高并发 TTFT**：C=10240 时 EP4 TTFT（~13s）远低于 TP4（~93s）。
6. **实际建议**：
   - 追求峰值吞吐（C≤2048）：优先 EP4（标准或 ampere_ep 均可），峰值约 14k output tok/s。
   - 追求高并发容量（C≥1024）：EP4 显著优于 TP4，但需接受极高延迟。
   - `ampere_ep` 可作为标准 EP4 的等价替代，略优但差距不大。
